# AeRift Alpha 0.1 gesture engine

## Interaction

Camera gestures are off by default. Enable them in **Control Center**. With the workspace in the foreground and an eligible file and peer or a pending offer, recognition starts automatically after camera permission. Show one open hand, make a fist until the instruction changes, then open the same hand again to offer the file or confirm acceptance. A pending offer can make the camera listen when gestures are enabled. Acceptance still requires the full gesture. If several offers are available, choose the intended offer before proceeding. **Send file** and conventional acceptance are always available.

The port retains the original one-hand open → grasp → release sequence, the three-sample minimum, 200 ms initial dwell, both 130 ms confirmation dwells, and interruption on a 220 ms capture gap. AeRift freezes the target and expires each camera attempt after 30 seconds, even if no hand is detected. A still-eligible, authorized camera can rearm after a short pause. A denied, unavailable, or busy camera requires intentional retry from Control Center. Each attempt gives users three seconds to form a stable fist and three fresh seconds to reopen the same hand. It rejects observations more than 150 ms old and consumes the intent before dispatch. The shortest observable pose dwell totals 460 ms, plus frame intervals, inference, and the user's transition time. Thresholds are Alpha defaults pending physical measurement.

Hide, blur, source change, ambiguity, stale inference, or target invalidation interrupts a started attempt. MediaPipe Web uses the three 0.6 inference thresholds from VoyageWright and does not expose a per-result presence score. Vision joint confidences are used when available. Handedness is never used as a confidence score or to identify a person. The posture calculation uses distances and is mirror invariant. Windows mirrors the preview via CSS only and uses the actual image aspect ratio. The iOS provider uses an unmirrored front camera, rotates into portrait, and converts Vision's lower-left origin to upper-left. Its 2D coordinates use zero depth and require separate threshold qualification.

## Host wiring

Render the shared `GestureControl` inside the workspace gesture slot. Supply the current `TransferControls`, the persisted opt-in and a platform camera factory. The component publishes camera status for navigation and Control Center, reveals instructions after detection and shows the Windows preview during an interaction. It creates a fresh intent and uses `bindTransferGesture` to freeze the file and peer or the pending offer and peer. On release the binding revalidates both identifiers and calls the same guarded `send` or `accept` action as the conventional controls. The older `mountSendGesture` adapter still serves the standalone photographic replay.
Construct a fresh `GestureIntent` for each explicit gesture attempt, using an app-generated unique ID and the current opaque selection and peer IDs. Create a `WebGestureCamera` on Windows or `NativeGestureCamera` on iOS. Surface the feedback message and dwell progress beside the selected file and peer, with a visible camera-off control. Announce changes of phase/status in an ARIA live region rather than announcing every frame.

The app-contract v1 commands **arm**, **release**, and **interrupt** remain local. Release consumes the intent before any transfer work is awaited. The binding checks the live selection or pending receipt, then calls the guarded conventional action. Conventional actions and target changes invalidate recognition context. Host deactivation, navigation, camera source changes, and disposal stop capture. Automatic rearming creates a new intent ID and requires the whole gesture again.

### Windows

The browser camera adapter reuses the Reach/Sextant pattern of explicit foreground capture, a single lease, bounded startup, one bitmap in flight, and teardown. It schedules recognition against a 64 ms minimum capture interval, giving a slow inference the next available video frame without a fixed delay after the result. It requests video only and honors existing WebView2/OS camera permission. On the trusted local app origin, ship `gesture-assets/` under the frontend public directory and resolve the classic worker URL from that origin. Allow same-origin model fetches in the host CSP (`connect-src 'self'` plus existing IPC) and allow same-origin workers and WASM evaluation (`worker-src 'self'`, `script-src 'self' 'wasm-unsafe-eval'`). Keep permission bound to the trusted origin. A missing capability or denied permission leaves ordinary controls available.

### iOS

The iPhone app uses the portrait front camera through [the native AVFoundation and Vision provider](../../apps/aerift/src-tauri/src/platform/ios/swift/Sources/HandCamera.swift). Tauri's production WKWebView uses a custom scheme. The Windows worker adapter requires a same-origin HTTP(S) worker. The native provider keeps video in-process and forwards normalized landmarks and camera state across the trusted bridge. It stops capture on lifecycle and interface-orientation changes.

[The iOS workspace adapter](../../apps/aerift/src/ios/IosGestureCamera.tsx) creates one camera port per trusted WebView and provides start, stop, camera-state and landmark events scoped to an attempt. The camera clock uses the native capture timebase. The port registers its event channel once, drops retired attempt events, and waits for the prior stop acknowledgement before starting again. Both the gesture and the Send button invoke [the same AppPort action](../../apps/aerift/src/nativeAppPort.ts). ## Source, rights, and performance

Source revision [fc813a4c03a4916c6b0aab346abbb8b1caa8cf38](https://github.com/Kgray44/treasurehuntSoT/tree/fc813a4c03a4916c6b0aab346abbb8b1caa8cf38) in `Kgray44/treasurehuntSoT`. The [VoyageWright proprietary license](https://github.com/Kgray44/treasurehuntSoT/blob/fc813a4c03a4916c6b0aab346abbb8b1caa8cf38/LICENSE.md) reserves rights. [AeRift issue #5](https://github.com/Kgray44/AeRift/issues/5) and the Alpha integration guide record owner authorization to use the relevant work. Source intake was limited to Crossdeck's `chart-transfer-gesture.ts` and test-fixture shapes, Watchglass's `hand-provider.ts` continuity rule and `public/reach/hand-worker.js`, and the capture patterns in `src/sextant/camera.ts` and `src/reach/browser-runtime.ts`. Reach's pointing, target calibration and interaction UI are outside this flow.

VoyageWright detects palm regions and 21 hand landmarks with MediaPipe Tasks Vision 0.10.32 CPU/WASM and the Hand Landmarker float16/1 task. It infers open/fist via finger geometry. The same provider also serves separate Reach pointing and manipulation interpreters. Its 640×480 browser capture uses a classic worker with a single transferable bitmap in flight and a 40 ms delay after each result. Its published Chromium photograph replay recorded p95 inference of 44.8 ms, p95 capture interval of 91.5 ms, and p95 capture-to-canvas age of 115 ms across 400 inferences. The measurement excludes camera exposure and display scanout and does not qualify a webcam, WKWebView, or physical iPhone. [VoyageWright replay evidence](https://github.com/Kgray44/treasurehuntSoT/blob/fc813a4c03a4916c6b0aab346abbb8b1caa8cf38/Development_Docs/Testing/Product_Experience/evidence/reach-d1-632e1895/worker-performance.json)

Runtime and model rights were checked separately. The [MediaPipe runtime](https://github.com/google-ai-edge/mediapipe/blob/master/LICENSE) is Apache 2.0. Google's [Hand Tracking model card](https://storage.googleapis.com/mediapipe-assets/Model%20Card%20Hand%20Tracking%20%28Lite_Full%29%20with%20Fairness%20Oct%202021.pdf) states Apache 2.0. The originating [pinned asset manifest](https://github.com/Kgray44/treasurehuntSoT/blob/fc813a4c03a4916c6b0aab346abbb8b1caa8cf38/public/reach/vendor/asset-manifest.json) identifies the exact task and runtime bytes. Third-party binaries are staged unmodified from upstream, with the license present in the staged bundle. No runtime dependency installation or network delivery of model assets occurs from the camera adapter. Apple supplies the iOS detector in the OS.

### Stage assets for the Windows host or test

Extract [MediaPipe Tasks Vision 0.10.32](https://registry.npmjs.org/@mediapipe/tasks-vision/-/tasks-vision-0.10.32.tgz), obtain [Hand Landmarker float16/1](https://storage.googleapis.com/mediapipe-models/hand_landmarker/hand_landmarker/float16/1/hand_landmarker.task) and [the upstream license](https://raw.githubusercontent.com/google-ai-edge/mediapipe/master/LICENSE), then stage the checked assets with Node. The worker verifies the model digest again before loading it.

```sh
node packages/gestures/runtime/stage-assets.mjs <extracted-package-directory> <model-file> <license-file> <public-directory>/gesture-assets
```

## Validation

Run the deterministic gesture and adapter cases from the repository root after installing the root tooling.

```sh
npm run test:gestures
```

The optional Chromium replay in `tests/gestures/replay.mjs` uses separately installed playwright-core 1.56.1, a Chromium executable, a disposable browser profile, and a scratch root containing the staged `gesture-assets/` and [Google's pointing-up test photograph](https://storage.googleapis.com/mediapipe-assets/pointing_up.jpg) (SHA-256 `ecf8ca2611d08fa25948a4fc10710af9120e88243a54da6356bacea17ff3e36e`). The replay feeds a canvas video through the actual worker, expects sustained hand detection with no send command, and checks teardown on camera loss. The command tests send synthetic landmark sequences.

For the full photographic sequence, put Google MediaPipe fixture files `right_hands.jpg` and `fist.jpg` in the scratch root and pass `offer` as the fifth argument to `replay.mjs`. The runner verifies both hashes. It crops one open hand and aligns the two palm regions. A browser click activates the same control the host can mount. The actual worker sees open, fist, and open twice using fixed playback timestamps. The control must report one offered transfer through the fixture callback and stop the camera after that offer. For the slower sequence, use `paced-offer`. It holds the first open pose long enough that a successful release falls beyond the old single three-second window. The timing replay, fixed-time pose replay, and synthetic command tests provide software evidence. Physical camera, transport and native-device behavior require the run below.

On Windows, the capture-timing revision `7b32861a228185fcf60234ce08f3397cd1757df9` produced one fixture offer in each of six photo replays covering normal, paced, dimmed, mirrored, smaller and moving hands. Occlusion, simulated mute and timeout each produced zero offers. All nine cases released the fixture capture track. The p95 gap between processed frames was 66.1 ms in the paced case and 73.9 ms in dim light. For physical acceptance, use the installed Windows app and an installed physical iPhone build on the same LAN. Record exact build SHAs, OS/runtime versions, lens direction and lighting.

1. Pair the devices. Verify that button send and receive work with the camera off. Select an ordinary file and an online paired peer.
2. Enable gestures. Check that the UI displays the selected file, peer, and camera instructions. Perform open → fist → open. Confirm one offer in the receiver UI and one invocation of the shared action. Hold or repeat the gestures without a fresh activation and verify the offer count stays at one. Accept with the receiver button and compare saved SHA-256 and size. Swap sender and receiver and repeat.
3. Record the terminal status when an attempt ends. The status distinguishes expiry, a frame gap, stale recognition, and loss of hand tracking. Collect the status text without saving camera frames. Exercise flicker, ordinary hand movement, multiple hands, occlusion, bright/dim lighting, either hand, moving out of frame, changed file/peer, camera denial/revocation, losing window focus, iPhone lock/background/rotation, and disappearing peer. Watch for an unintended offer and verify tracks stop and the buttons remain usable.
4. Collect at least 20 intentional attempts in each direction and 50 no-intent opportunities per device during the pilot. Record success/abort rates, false activations and duplicates, median/p95 capture-to-feedback and release-to-offer, and times spent waiting for tracking. Separate software timing from sensor/display timing. A duplicate or unintended offer keeps the device gate open.
