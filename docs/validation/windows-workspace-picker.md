# Windows Workspace chosen-folder metadata pilot

This follow-up to the qualification-only #109 wires a **local, read-only, single-folder metadata panel** into ordinary installed Windows Workspace → File Browser. It does not add file opening, child navigation, import, transfer selection, sharing, deletion, shell access, or any new generic plugin permission. Saved Workspace files and the receive-folder picker are unaffected.

- Only the bundled Windows main document can call the three narrow commands. The chooser additionally requires the owning window to be focused and the user to complete its parented native dialog. The development HTTP origin is deliberately outside this trust boundary. The app never accepts a path, handle, URI or default location from renderer input.
- Each explicit chooser invocation has an opaque request ID used only to revoke that invocation. The returned grant and one-use cursor separately authorize the next metadata page. The native host retains at most one current pinned fixed-NTFS directory and one chooser. Cancel without choosing keeps a prior grant; choosing a valid replacement drops it. Revocation, main-window close (including close to tray), destruction, expiry, end of listing and native read failure release the appropriate grant. Clear/route teardown cancels a matching pending result without authorizing a new chooser. The component ignores stale responses, including a late native callback after route teardown.
- List results include only leaf display names, byte counts for files, and another cursor if available. The renderer displays only one current, non-persisted page; no path, file identity, bytes, hidden/system entry, reparse point or placeholder is exposed. A missing/expired grant requires another explicit native selection.

## Exact evidence required before merge

Run the normal Windows application lane against the candidate, not just #109's isolated feature compile. Run `cargo test --locked -p aerift-transfer --features windows-folder-picker-qualification --lib folder::windows_handles::directory_page` and `cargo test --locked --manifest-path apps/aerift/src-tauri/Cargo.toml --lib workspace_folder_picker::tests` on a disposable Windows runner. Do not count a test binary's successful compile as execution.

Install the ordinary unsigned test package with no qualification CLI or build flags, in a disposable Windows guest with synthetic fixed NTFS paths exclusively. Verify that opening Workspace or Files shows no local content and no native prompt; click **Choose folder** once, cancel, then explicitly choose the synthetic directory. List the expected entries and confirm no absolute location, sibling, excluded metadata, nested entries, file content or new import/transfer becomes visible. Validate next page from the granted directory, replacement, explicit clear, leaving and returning to Files, an idle five-minute expiry (including native handle release), and closing the owning window while the native picker is open. Confirm the installed app enters the panel through the normal Files route, and confirm the same release package does not expose the panel or native handlers on another platform. Record the exact app revision and installer hash along with distinct compile, test execution and installed UI results. Do not test with personal folders or devices.
