# Desktop Workspace browser: bridge-free Windows proof

**Status:** Compile/policy qualification only. The standalone test target is opt-in, does not create or navigate a WebView, and is not imported by the app. No installed product behavior or arbitrary-site browsing is claimed.

## Architecture decision

AeRift main 7527087 locks Tauri 2.12.7, tauri-runtime-wry 2.12.5, Wry 0.57.3, and webview2-com 0.39.1. Tauri's [managed WebView preparation](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.7/crates/tauri/src/manager/webview.rs#L130-L264) adds invoke initialization, plugin scripts and app/IPC schemes; its [final preparation](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.7/crates/tauri/src/manager/webview.rs#L512-L517) attaches the message handler. [Tauri 2.9.5 does likewise](https://github.com/tauri-apps/tauri/blob/tauri-v2.9.5/crates/tauri/src/manager/webview.rs#L462-L467). A remote-origin capability check is useful defense in depth, but denying commands is not the same as not exposing an AeRift bridge. Leave the primary Tauri window's CSP and capabilities unchanged. Do not make it an iframe or use a second Tauri-managed remote view.

A **raw Wry child of the trusted Windows HWND** can live inside the Workspace without ever becoming a Tauri-managed webview. [Raw builder defaults](https://github.com/tauri-apps/wry/blob/wry-v0.57.3/src/lib.rs#L810-L851) provide no IPC, initialization script, or custom protocols. [Wry Windows setup](https://github.com/tauri-apps/wry/blob/wry-v0.57.3/src/webview2/mod.rs#L470-L502) only installs those bridges when supplied. Windows child HWND construction and DPI-aware repositioning are provided by [Wry](https://github.com/tauri-apps/wry/blob/wry-v0.57.3/src/webview2/mod.rs#L92-L104). The candidate adds no equivalent bridge and never evaluates site-provided script. It also disables native web messaging and host objects before loading remote content as described by [Microsoft](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security).

A temporary user data folder creates a separate WebView2 browser-process group ([process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)). This is not an OS sandbox for the Rust host: that code remains in the AeRift process. If the threat model requires process-level egress confinement, put this session in a separate restricted helper before opening arbitrary websites; a child HWND or hostname filter cannot enforce that boundary. Until then, keep external-browser fallback.

## Staged native files and scope

- `workspace_browser_policy.rs`: bounded exact build/admin policy origins; HTTP(S), credential-free, no IP literals, local/private hostname suffixes, custom schemes, storage URLs or alternate ports. No script can extend the allowed origins. The policy must start empty/disabled until trusted configuration supplies explicit allowed origins. It is a URL policy, not an address-resolution or network policy.
- `workspace_browser_sandbox.rs`: Win32 STA-owned Wry child initially blank and hidden. Dedicated unique scratch data root, verifies InPrivate mode and reported WebView2 profile path before first approved navigation, denies download starts, new windows, permission requests (including clipboard-read), WebView2 clipboard opt-in, external drops, autofill/password saving, app-region capture, default dialogs and external URI launches. Adds separate frame navigation and [all-source request controls](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_22): document, shared worker and service worker. Returns an inert response for denied resource requests; redacted typed host errors, never a URL or page in a host log. Closing drops the raw controller first, then attempts temporary-directory removal. Windows process-exit cleanup may still need a bounded private scratch scavenger.
- Candidate assumes a trusted native scratch root whose ancestors have been validated, not arbitrary renderer input. It checks the final base for a reparse point. A future host owns allocation/cleanup, DPI bounds, visibility and focus. It must fail closed to explicit external browser if the required COM interfaces, profile isolation, or any security-hook registration cannot be confirmed.

This candidate intentionally does not expose live title/URL events, tab actions, clipboard, uploads, user download integration, arbitrary developer/shell commands, or automatic history collection. No file picker or authenticated web page was exercised. Modern browsing can require additional permitted origins; do not translate arbitrary page redirects into approvals. Request interception cannot guarantee IP-level isolation, DNS-rebinding protection, WebRTC or every browser-internal request; never market it as such.

## Minimal implementation and test-plan gate

1. Use an isolated **Windows-only qualification harness**, not the current AeRift production window, separate account/data roots and no outbound Internet traffic. Declare already locked Wry 0.57.3, webview2-com 0.39.1, raw-window-handle 0.6.2, Windows 0.62.2 and tempfile as direct target dependencies if needed. Do not introduce a new browser version yet. Compile the two files, run their policy unit tests, then qualify the Win32/COM types. Once behavior passes, add a test-only native harness featuring an explicitly approved synthetic HTTPS fixture origin and no live-site data. Fixture must be routed inside the disposable runner and its test policy must not leak into the ordinary application. Never disable browser TLS checks.
2. Launch a single raw child under a trusted parent on the STA **after the current callback returns**. Verify the rendered fixture has no Tauri/internal IPC globals or WebView2 messaging/host objects. The test can use its own fixed introspection probe, absent from release code. Verify blocked redirects (top-level and child), no popup surface/no system scheme launch, no downloaded bytes, no external file drop or permission promotion, and no new page activation on setup failure. Validate scripted browser resources remain within fixture origins and do not touch privileged app handlers. Use inert synthetic assertions only.
3. Verify actual profile and browser process differ from the trusted app, media permission/storage unaffected on the parent, no automatic host clipboard read or bridged clipboard, no seeded privileged storage in the child and bounded cleanup after browser shutdown. Record runtime minimum, DPI updates, focus restoration, minimized state, category navigation/scroll, modal overlap, paint clipping and close during navigation. Browser-pane placement should be a stable native rectangle inside a nonoverlapping Glass chrome slot, not a transparent overlay that claims to be a CSS child. If the raw child can obscure a native dialog or app modal, hide it synchronously before showing that control.
4. Only then privately wire trusted tool actions (approved Navigate, Back, Forward, Reload and Close), plus validated/redacted display metadata if needed. Require exact trusted caller labels (main WebView as well as native window) and trusted app origin; keep the child out of Tauri's manager. Do not expose script execution, changing browser policy or general HWND manipulation over IPC. Add release Windows CI for the runtime fixture before enabling approved origins outside the harness. If policy requires public-web browsing with enforced private-address denial, qualify an egress-restricted helper/reconciled browser architecture before broadening scope. iOS Safari Services and Android Custom Tabs remain unchanged.

## Workspace experience contract

- **Desktop:** a Glass sidebar for Recents, Saved and saved-site groups; a native page viewport on the right. The address field and small Back, Forward, Reload, Save and Open in Default Browser icons live in trusted app chrome along the viewport's top. The native page rectangle starts below the controls; a site cannot draw over the trusted address or fallback controls.
- **Mobile:** the same saved-site organization, library-first navigation and full-screen reading when an independently isolated native pane qualifies. Keep the system browser option on both platforms. Do not present existing Custom Tabs or Safari Services as the embedded pane.
- **Privacy:** history off by default and clearable; save explicitly from a native-validated HTTP(S) address. Do not import system history, copy profile/cookies, or store typed credentials or search history. Account sign-in, app permissions, downloads and file selection stay disabled in the proof.
- **Native boundary:** no iframe, no app IPC in remote content, no relative resolution into the app's internal schemes, and no public browsing activated until the independent runtime boundary and native controls are verified. Validate external opening via the existing explicit native safe URL opener, never via arbitrary URI schemes from the page.
