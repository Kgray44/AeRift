# Activating folder offers without changing file behavior

## Linux commit primitive

The separate Linux-only `Receiver::commit_resumable_folder` command boundary is a library API, not an app/IPC command. It needs the completed Remote receipt, explicit folder capability, a native-confirmed existing destination, and the profile's stable private scratch/ledger. The host must never accept scratch or ledger from a remote peer or browser, or change ledger directories between calls. Keep the ledger through restarts and independently of transfer stage cleanup. At the next app integration pass, constrain construction of this profile capability to the protected native store.

Directories are pinned by Linux descriptors with all symlink and magic-link traversal denied. The chosen destination is an existing directory, not a path from the sender. The received directory name comes from the verified strictly portable single-root manifest, not the archive filename. Files and directories are fully checked and synced in private staging before a same-volume, descriptor-relative `RENAME_NOREPLACE`. An existing file, directory, or symlink is never replaced. Nothing is merged into an existing tree. No path-based rename fallback is allowed when the kernel or filesystem rejects it.

A durable exclusive reservation records the authenticated peer fingerprint and transfer UUID before the final publication. The reservation cannot be overridden by a new name, manifest or chosen directory. A crash before rename, a race that introduces a filename collision, or a sync error may leave a spent receipt without confirmed publication. The current API fails closed rather than retrying that receipt. If rename succeeded and a later sync fails, the complete tree can already be visible. Do not report it durable without sync. Do not treat an unconfirmed result as permission to overwrite or purge. Local same-user/admin processes are trusted to preserve the profile-managed directories and ledger. The receiver's envelope and private staging briefly require up to roughly twice the source bytes.

This is not qualified for Windows (including reparse points, NTFS ACLs or OneDrive), Apple platforms, Android or filesystems without kernel no-replace support. In Windows, do not substitute pathname `MoveFileEx`/rename with prechecks. Use a handle-relative, same-volume no-replace directory rename and reject every component marked as reparse by opening each leaf relative to a pinned ancestor without following the leaf, with restrictive profile DACLs. Qualification needs real directory junctions/symlinks, an occupied empty directory, concurrent publisher and replay after restart. Windows must advertise no safe folder-publication capability until then.

## Compatibility and consent

1. Add an authenticated Remote-only capability exchange with an explicit versioned **FolderManifestV1** feature. Separate send and receive commitment, and advertise receiving only when native folder publication and the profile ledger are available. A missing/unknown capability means unsupported: no offer and no reinterpretation as a raw archive. The existing files and windows continue using their original V1/V2 paths unchanged.
2. Add a distinct Remote-only typed offer admission endpoint. Pin the mandatory representation id, peer fingerprint, transfer UUID, canonical envelope size and SHA-256 as one immutable signed-by-transport offer. Include verified display title, total files and total bytes in a bounded metadata frame. Bind display fields to the canonical manifest; fail if the decoded manifest disagrees. Do not use the archive filename, extension or magic to decide acceptance or export. Reject a duplicate UUID with a different representation or metadata, including in recovery.
3. Show typed folder metadata in the ordinary Remote consent flow. Explicit file or gesture readiness cannot accept a folder. For a folder the native user separately chooses the destination; an opaque picker/session reference, not a typed webview filesystem path, is retained with the receipt. Resolve all relative names inside the verified single tree. Revocation and cancellation invalidate in-flight staging before the final commit admission. The destination is never advertised to the sender.
4. Use the shared checkpoint engine from accepted offsets only after typed admission. Persist protected type/consent/receipt scope across the existing journal and request fresh native confirmation on uncertain recovery, never inferring type from stored bytes. Commit using the protected receipt and approved destination; only a successful durable publication is “Folder delivered”. An accepted envelope is not a folder delivery receipt.
5. Keep routes and UI disabled for hosts lacking proven native safe commit, and test old-peer no-downgrade, raw file named like the envelope, forged or replayed errors, destination substitution, revoke/cancel, interrupted ACK and duplicate commit. This change publishes no app command or network route.

### Typed record codec

The shared `folder::admission` codec defines a 2 KiB strict control frame and a distinct `FolderManifestV1` capability. The transport adapter must supply the already-authorized Remote TLS sender ID, local recipient ID and a dedicated, fresh, Remote-folder TLS exporter binding from the same live connection. Do not accept a binding from IPC, a header, a second connection, or a user-supplied body. Re-admission after reconnect requires a fresh connection binding and matching immutable commitment. Persist the commitment before granting consent and compare it on every fresh admission for the same authenticated peer and UUID. Before any export, compare the reconstructed canonical framing bytes (magic, length and JSON), root title and entry count to the admitted record, then use the already-pinned envelope receipt. The codec is not a network dispatcher; its tests use synthetic bindings and do not prove an actual TLS exporter exchange. No installed host advertises this feature yet.

### Windows native qualification blockers

Microsoft's [FILE_RENAME_INFO contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) documents relative target-directory handles and disabling replacement. The [native rename remarks](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) specify same-volume publication and the source DELETE permission. Existing app storage only implements protected file replacement and profile locks; it does not expose a trusted, local-volume, reparse-checked destination directory capability. A dedicated, headless Windows runner fixture must actually create NTFS junctions and race a destination exchange/collision with export, preserve pre-existing files and directories, prove the durable replay ledger across process restart, and check directory recovery after interrupted publication. Keep Windows capability absent until native implementation and proof exist; no Windows UI or physical camera test is required to start that fixture.

A `cfg(all(windows, test))` qualification primitive now exercises actual Windows directory handles without registering an application action. It opens synthetic local NTFS descendants one validated leaf at a time through `NtCreateFile` using a held ancestor, `OBJ_DONT_REPARSE`, `FILE_OPEN_REPARSE_POINT`, and a post-open handle attribute check. The primitive rejects non-NTFS and keeps DELETE sharing off for held handles. Publication uses `SetFileInformationByHandle(FileRenameInfo)` with a held target directory and the replacement flag clear. The receipt marker uses a relative exclusive create with write-through plus file flush. The native host still needs to supply protected root capabilities and a path-free verified staging adapter, and power-loss durability remains unclaimed.

For the headless Windows fixture, use the standard Windows Actions runner with stable MSVC and a local NTFS temp directory, and run this exact filtered CI command from repository root:

```powershell
cargo test --locked -p aerift-transfer --lib folder::windows_handles::tests -- --nocapture
```

The synthetic fixture requires no external network/listener, interaction, account, administrator or third-party approval. It creates a real directory junction with `mklink /J`, probes blocked parent substitution and existing empty-directory collision, races a no-replace rename against a competing leaf creator, verifies staged content and empty directories after publish, and starts a fresh subprocess to show a previously spent receipt is denied while a new receipt can be created. A standalone MSVC target type-check does not replace executing these assertions. Ordinary installed file flows and #81 native UI are not changed.

The Windows qualification path also exercises the full receiver operation in `ntfs_typed_completed_receipt_is_verified_staged_and_published_once`: a real completed resumable receipt gates export, and the typed envelope and metadata commitment must match it. A handle for the protected envelope is revalidated and streamed through the shared parser. Files and directories inside the private stage are created one leaf at a time relative to held handles, with digest and file-flush checks. Nothing becomes visible at the selected destination until a one-use marker has been written and a single no-replace handle-relative rename succeeds. Cleanup operates only on known private stage entries opened by relative handles. Qualification checks rejection before consent/completion, tampered envelope, cancel, different-destination replay and revocation, plus successful bytes and empty directories. This test-only wrapper deliberately takes distinct Windows capabilities and cannot use the Ambient A7 Inbox/Explorer file grant. A trusted native picker/profile adapter still must establish those capabilities and apply profile DACLs; the synthetic helper does not grant product authority. A real NTFS run and hard-power-loss durability are separate.

### Isolated destination capability and cross-restart admission

The test-only Windows selection producer accepts an absolute fixed-DOS-volume path from the native picker boundary, rejects UNC, device-prefix, SUBST and drive-relative paths, verifies the opened root against the NT volume mapping, then opens and retains every descendant directory separately. Reparse points, namespace changes and unqualified volumes fail closed. The high-level verified NTFS fixture uses this producer for its synthetic picker result instead of granting destination authority from a path string. The ordinary installed UI does not yet invoke a folder picker for Remote.

The shared admission store records only `(peer fingerprint, transfer UUID, immutable typed-offer commitment)`, under the versioned `remote_typed_folder` scope. The isolated Windows profile adapter uses its existing DPAPI-protected, write-through replacement file and the existing exclusive profile lock. No title, destination, acceptance, source, payload or TLS binding is written to the record. Reopening the store accepts the same immutable commitment only after fresh live channel authentication; any new destination and incoming consent are acquired separately. A raw-v2 offer is not an admission record. The profile has a fail-closed 1,024 record capacity; no automated eviction or Replay reset is introduced.

The native DPAPI qualification uses `cargo test --locked --manifest-path apps/aerift/src-tauri/Cargo.toml --lib windows_dpapi_remote_folder_records_survive_store_reconstruction`. This is separate from the headless transfer library fixture. Neither qualifies on-host Windows picking or enables a dispatch route. The remaining narrow adapter work is to attach this producer after `blocking_pick_folder` in a protected ingress-only session, persist the immutable typed offer before user confirmation, and bind the protected admission and real Remote TLS bearer to the accepted checkpoint and typed completion. Regular file offers are untouched.

### Authenticated checkpoint integration

The shared `serve_admitted_folder_request` is separate from ordinary v1/v2 and Friends dispatch. It is intended only for a previously authorized Remote-folder transport and a dedicated receiver scoped to folders. It requires the authenticated sender, checks live grant and exact admitted peer/UUID, re-parses every POST offer and demands the identical envelope, then reuses the existing v2 explicit acceptance and bounded checkpoint rules. A caller must not hand it a generic Nearby or Friends grant. Ordinary v2 bodies flow through their existing registration and decision path.

The isolated qualification test `cargo test --locked -p aerift-peers actual_pinned_remote_folder_tls` creates fresh AeRift certificates and genuine pinned mTLS over a loopback TCP connection, using a distinct `aerift-remote-folder/1` ALPN. It proves protocol separation, wrong certificate denial, channel-exporter replay rejection, mismatched transfer UUID rejection, matching capability, independent receipt acceptance, one connection cut after a committed PUT, verified resumed envelope, and exact staged member bytes with empty directories. A terminal v2 receipt means envelope verified only, not “Folder delivered”. The folder exchange remains a synthetic eligibility test; neither a production Windows listener nor an installed folder action is registered. There is still no independent-uplink claim.

### Opt-in live Remote listener seam

`RemotePeerNode::serve_with_folders` attaches a qualified folder ingress to an existing explicitly private Remote socket and rejects reuse of the ordinary receiver's staging location. The old `serve` API does not advertise the folder ALPN. On the opted-in listener, each TLS connection selects either ordinary Remote or the distinct folder ALPN; mutual certificate identity and the existing Remote trust grant are checked, including on every request. The folder ALPN alone never grants authority, does not support discovery or pairing and never dispatches ordinary v1 or nonadmitted v2 requests. The sender `send_folder` uses only the folder ALPN, verifies Remote possession and negotiated cap, fetches the same-connection TLS exporter for the typed offer, then uses the protected admission and v2 checkpoint implementation. It never tries legacy as fallback.

This creates a live native Rust transport option, not an installed Windows action. The next native adapter should construct the protected folder ingress only within the already-exclusive Windows Remote session, retain one profile-private folder receiver, attach it to the existing explicit overlay listener, and bind its inspection API to the native selection capability. `respond(key, true)` is reserved to explicit native destination-and-offer review, never Remote-ready or cross-lane state. A folder envelope receipt is distinct from export; only the successful verified no-clobber export can drive the delivered UI. Keep the installed capability disabled until the actual headless NTFS/DPAPI fixtures pass and durable delivery reporting is qualified.

### Installed Windows source binding (qualification only)

The standard Windows build ships with the folder capability disabled. A private build must be made with the nondefault `private-remote-folder-qualification` feature, be in exclusive Private Remote mode at a previously authorized exact overlay endpoint, and explicitly select **Enable private folder qualification** before starting the session. The old developer mode and ordinary Nearby/Friends are never granted this route. No retries fall back to the file lane. `PrivateRemoteFolders` is hidden unless native snapshot reports that the specific session enabled it.

Only native Windows dialogs can select a source or destination. The incoming action shows the typed title, count, bytes and peer, then **Accept folder and choose destination** opens the picker. The native adapter pins and retains the chosen destination before sending acceptance. Ordinary file approval cannot accept a folder. The completed envelope and the destination capability are joined only by exact protected receipt and live grant, with separate **Save verified folder without replacing files**. Stop/revoke prevent continued app actions. The strict no-replace native publisher uses its separate profile staging and receipt ledger; sender UI clearly distinguishes verified envelope from successful local export. No destination, binding or approval is persisted across relaunch.

```powershell
npm run tauri --workspace @aerift/app -- build --features private-remote-folder-qualification --bundles nsis
```

A qualified installer fixture should exercise the normal Remote shell with feature off and private feature build with checkbox off and on; confirm no folder discovery or implicit listener, typed/plain separation, dialog cancelled and destination-junction denial, existing directory untouched, exact verified files exported, visible result only after publication, refusal/revocation, and same receipt restart no-replay. Keep the release flag off pending real NTFS/DPAPI/installer evidence. This branch adds no installer workflow, publishes no product and does not use any live account or household network.
