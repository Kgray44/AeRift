# Ambient A7: explicit Inbox receiving

This slice adds a Windows Activity Inbox for incoming **regular files** without changing the ordinary configured receive folder, peer discovery, or the existing partner and recipient approval model. A pending offer exposes separate **Accept to receive folder**, **Accept to Inbox**, and **Decline** actions. Consent chooses exactly one branch. The ordinary manual and pre-existing gesture acceptance path still uses the configured receiver folder; no new gesture consumer or implicitly authorized destination is installed here.

The native receiver freezes the Inbox branch and its host-owned root under the same lock that accepts the pending offer. Size, trust, cancellation and full digest checks run through the existing v1 authenticated streaming receiver before publication. A per-offer directory with an opaque name contains an inert file plus a separately synchronized final receipt marker. The app session folder is private to the app's operating-system profile, not a peer-supplied or user-configured receiving directory. Missing markers are never exposed as completed. Files, receipts and temporary paths are never emitted in ordinary application logs or supplied through a network command. Neither the sender nor the webview can provide an Inbox path.

Activity can browse a bounded list and filter by case-insensitive name; the list describes recovery candidates and does not claim a current integrity check. **Check integrity** reopens the selected authenticated receipt and streams the stored content to validate precise size and SHA-256 before showing a positive result. Old incomplete transactions and storage errors fail closed; original storage is left alone if verification fails. Windows restart persistence relies on synced files; full filesystem power-loss behavior and recovery of partial transfers after reboot have not been qualified. The private profile is a trust boundary, not cryptographic protection against arbitrary code with the same user's access.

External destinations are not implemented by this slice. A captured proposal may be marked as requiring separate authorization using the native API, which only preserves bytes in the Inbox. There is no automatic browser opening, external editor insertion, file overwrite, arbitrary destination path, archive expansion, executable launch or remote permission escalation. This version does not automatically open Inbox entries, implement per-file deletion/retention settings, classify contents beyond the authenticated source offer, support contextual Explorer save, or integrate mobile/browser receive actions. Legacy configured receive and pairing behavior remain independent.

## Evidence

The same two-process TLS 1.3 regression fixture now sends a 3 MiB file in each direction to explicit Inbox and an empty file to the ordinary receive path. It checks Inbox absence before completion, matching authenticated peer and offer, directory contents, SHA-256, reopened search and verified receipts. Core regressions also cover same-size tampering, verified-only completion, binding to the specific peer and transfer, and ordinary path separation. Native Windows UI qualification requires the exact Windows installer test and an explicitly approved Windows fixture. No physical workflow was run.

### Windows authenticated restart receipts

The Windows app seals the terminal receipt under the current user's existing DPAPI profile with a distinct Inbox record domain before the receipt marker is published. Restoring a receipt refuses unknown/unsealed markers, wrong evidence domain, or a wrong offer/peer key; **Check integrity** additionally streams the exact stored payload and verifies its authenticated length and hash. Non-Windows library callers can explicitly choose the unsealed compatibility path, but Windows shipping uses the sealed path. This prevents raw disk modification from fabricating verification, not malicious software already running as the same Windows user. No automatic legacy marker migration or external storage authority is provided.

**Save a copy** is an independently authorized export, not implicit delivery to the active application. The native Save dialog supplies the target; cancelling never writes. The authenticated original is streamed to a temporary file in the chosen directory and verified in the same pass; only intact bytes are published, without replacing any existing file. Corruption, collision, or profile-private targets leave the original untouched and do not open or execute the result.
