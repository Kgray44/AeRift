# AeRift Remote: resumable transfer design

**Status: proposed, not implemented or qualified.** Reviewed against main at `85026413c232d2de076b89a9000a6f6d182c7477`.

## Baseline and decision

The v1 transfer already streams bounded buffers over a trusted peer connection, verifies the declared byte count and SHA-256 before publishing without overwriting, and keys received offers by authenticated peer plus transfer UUID. It is not resumable: v1 allows one full-body PUT; receiver-side EOF, timeout or I/O failure discards staging; sender recovery only polls status to handle a lost terminal receipt. Sender-side bytes read into the network stack do not prove anything was stored remotely. Keep v1 unchanged, including local-network behavior and downgrade compatibility.

Use a separately negotiated resumable protocol over the same pinned mutual TLS and native transfer runtime. A positive authenticated capability is required; absence or explicit unsupported means v1 is available, but never silently restart or downgrade an already-accepted resumable offer. Prefer sequential bounded chunks over extending v1 with a long ranged body: bounded commit points make acknowledgement loss, crashes and route migration predictable at the cost of one control exchange per chunk. Defer parallel chunks until data demonstrates a throughput need.

The first useful, independently reviewable implementation is **one consented single file, resumable after a connection loss while both processes remain running**, with one stable offer and no retransmission of acknowledged chunks. Document this scope explicitly; restart durability, folder transfer, mobile background operation and actual internet qualification are separate gates.

## Single-file protocol and storage

- Negotiate capability on an authenticated no-store request to the selected peer. Carry forward the existing validated file offer (UUID, name, byte length, digest). Scope all queries, cancellation and content to the authenticated peer and UUID; reject conflicting metadata on UUID reuse. Existing explicit recipient accept remains mandatory before the first byte. Do not use gesture readiness as implicit remote acceptance.
- Use ordered, explicit chunk offsets and lengths; a bounded chunk (e.g. 4–16 MiB) carries a SHA-256 digest and streams with bounded buffers into receiver-owned private staging. Reject offset beyond the committed prefix, overlap, size overflow, invalid length/digest, and concurrent uploads of the same offer. Never store or publish from a remote-provided path.
- A connection drop or idle timeout inside a chunk leaves the previous committed offset intact. Truncate any uncommitted suffix under transfer ownership before accepting a retry. After validating each chunk and flushing bytes, commit the new offset and then acknowledge it. A lost acknowledgement is resolved by querying the receiver rather than replaying side effects: sender seeks the **authoritative** offset on the same immutable source and same offer. A truncation, prefix/digest mismatch or impossible offset/length fails safely rather than overwriting verified output.
- Completion requires exact length and full-file SHA-256 (computed by streaming; optionally maintain an incremental digest while live). Flush and synchronize before existing no-clobber publication. An authoritative completed receipt (not 100% local send progress) is required for completion UI. Query after losing the final response; a repeated completion/status query cannot publish another output.
- Serialize chunk ownership, cancellation, trust revocation and final publication. Cancellation/revocation terminate retries and discard partial data; retryable route disconnect does neither. Bound bytes per offer/device and total reserved bytes, active sessions, retry attempts/quiet time, and staging TTL. Reap on startup and while idle when persistent staging lands. Avoid leaking partial payloads or remote paths in diagnostics.
- Initially stage partial data only for the lifespan of an accepted in-process offer. For crash/relaunch durability, add private transactional journal keyed by peer/offer/manifest, persisting offset only after the corresponding bytes are durable, truncating back to the last journaled offset on recovery, and reconciling the atomic-publish/receipt window so restart never causes a duplicate. Atomic crash recovery must be verified on each supported filesystem before claiming restart resume. On the sending side use a verified immutable staged source or a platform-scoped durable file permission; fail if the source can no longer be safely recovered.

## Queue, folders, and platform limits

Persist local intent and source handles, never files on the rendezvous/relay. Offer metadata and content only once the chosen trusted recipient is reachable; require acceptance for each new offer. An interrupted accepted transfer can auto-retry with bounded backoff while the grant is valid. Retry stops on decline, cancellation, expiry, changed source, or lost trust. Offer readiness is advisory and distinct from recipient consent, final receipt, and device reachability. Android requires appropriately managed foreground/user-initiated work; do not promise iOS continuation after suspension or termination for the current custom socket transport. The app must show paused/queued state truthfully and resume when the platform permits.

Add folders as an explicitly accepted, bounded, deterministic manifest and a set of independently verified files, not an implicitly extracted user-supplied archive. Validate relative paths/components and platform canonicalization/duplicate collisions before writing. Reject symlinks, traversal, special/device files, disallowed names and over-quota manifests. Materialize into a private staging directory; publish once without merging into an existing destination. Test empty folders, Unicode/case collisions, link swaps and incomplete tree cleanup.

## Acceptance matrix

1. Existing v1 sender/receiver and gesture/LAN suite remain unchanged. Unsupported vs failed capability reads cannot cause post-consent downgrade or side effects.
2. In an integration test use an authenticated synthetic transfer, commit multiple chunks, cut a connection inside a chunk, and restore a route. Observe nonzero receiver offset; only bytes after it are sent on the successful resumed path. Exact length and SHA-256 match, and one destination file exists.
3. Drop both a chunk acknowledgement and the final completion response; confirm status recovery, no duplicate side effect, integrity, and honest progress. Also exercise wrong peer/UUID, repeated/overlapping/out-of-order chunks, false offset and wrong digest, source edit, quota exhaustion, consent declined, trust revoked, and cancellation racing publication.
4. After adding journaling, hard-kill at file write, durable offset commit and publication, then restart and validate no missing, skipped or duplicate bytes and no duplicated output.
5. For real qualification, use two independently provisioned endpoints on separate uplinks with synthetic data only. Separately prove VPN, direct WAN and forced relay (when implemented), recording actual route, nonzero resumed offset, digest and verified receipt. Loopback, network namespaces and emulator fixtures are component/integration evidence only, not real cross-network qualification.
