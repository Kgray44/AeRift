# AeRift Remote v2 resumable single-file profile

**Opt-in development profile. Not enabled in desktop or mobile apps.** This profile requires an already authenticated and separately Remote-authorized device session. It does not introduce identity, directory, route disclosure, relay or grant type. Nearby v1 is unchanged. There is no automatic fallback after a v2 offer: an older receiver declines the version.

- `POST /v2/resumable/transfers` offers the existing canonical v1 `Offer` (UUIDv4, safe filename, size, SHA-256). The receiver returns its `Status`; it does not accept automatically. Identical authenticated peer, UUID, manifest and mode repeat idempotently. A changed manifest or a v1 offer under the same peer/UUID conflicts.
- `GET /v2/resumable/transfers/{uuid}` returns the authorized transfer status. At `transferring`, `bytesTransferred` is the prefix committed in the live private receiver stage, not sender bytes written. The only valid non-final offset is on a 1 MiB boundary. The initial accepted checkpoint is 0. A socket loss does not cancel an offer.
- `PUT /v2/resumable/transfers/{uuid}/chunks/{offset}` takes a canonical decimal offset, positive fixed `Content-Length`, and `application/octet-stream`, without transfer encoding. Each block is precisely min(1 MiB, manifest length minus offset). Future, overlapping, oversized, malformed, or unapproved chunks fail. An identical retry wholly inside the committed prefix leaves it unchanged; a differing retry fails. The response returns the authenticated committed offset. The receiver buffers at most one block per request and the existing connection cap bounds parallel requests.
- `POST /v2/resumable/transfers/{uuid}/commit` with no body succeeds only after the complete stage is rehashed, synchronized, and published without clobbering an existing file. All bytes staged is not completion. A duplicate commit after success replays the same receipt. A concurrent commit receives Conflict; the sender can read authenticated status. Zero-byte transfers still need approval and an explicit commit.
- `DELETE /v2/resumable/transfers/{uuid}` cancels and drops the partial checkpoint. An expired idle checkpoint or revoked Remote authority also drops it. A disconnected sender never issues DELETE merely to recover from a broken socket. An already-published result remains intact.

The sender preserves one transfer ID, learns the checkpoint from the same pinned identity, resumes at a validated nonregressing offset, and uses bounded reconnects. A local caller may retry a recoverable failure with the same UUID, filename and immutable source bytes. No file is published on digest mismatch. Transfer approval, recipient identity and source reauthorization can never be inferred from an offset.

## Current durability boundary

The staged prefix survives transport disconnection while the receiver process remains alive. Staged blocks and approval are not a durable journal; after process termination, resumption is not supported. There is not yet an app queue, crash-recovery reaper, folder manifest, or Friends winner transport adapter. Do not wire this into background or release defaults. A restart-safe journal must transactionally reconcile checkpoint, expiration, revocation, user approval and publication/deduplication; see [the staged design](../../docs/superpowers/specs/2026-11-24-aerift-remote-resume-design.md).
