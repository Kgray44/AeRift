# AeRift protocol v1

This document defines the peer protocol. [The TypeScript interface](../../packages/app-contract/src/v1.ts) defines the app-facing API. Field names and wire literals below are case-sensitive. Use UTF-8 JSON, ignore unknown response members within v1, reject unknown versions and never fall back to insecure transport.

## Discovery and identity

Advertise DNS-SD service `_aerift._tcp.local.` with the TLS listener port. TXT records are `v=1`, `id=<device ID>`, `name=<UTF-8 device label>`, and `platform=<Platform>`. A device ID is the lowercase 64-character hex SHA-256 digest of its stable self-signed leaf certificate DER. Use an ECDSA P-256 leaf and TLS 1.3 with HTTP/1.1 ALPN. Keys must come from the OS CSPRNG and remain native, with protected storage (Windows DPAPI-backed storage and iOS Keychain). Treat discovery metadata as untrusted display and routing hints. Deduplicate by ID, mark peers offline on removal or TTL expiry, and keep saved pairings available. Key replacement requires re-pairing.

## Pairing

The device receiving the pairing request creates an invitation locally for an explicit user action. The invitation format is `aerift:v1:<recipient device ID>:<token>`. The token is 32 random bytes encoded as unpadded base64url. Show a copyable code in the pairing UI. QR display or scanning can use that same string. The same LAN DNS-SD result supplies the endpoint. Expire invitations after five minutes and rate-limit attempts and concurrent untrusted connections. Keep tokens in memory and out of logs, telemetry, discovery, URLs and persistent storage.

The redeemer pins the TLS server leaf to the fingerprint in the invitation before sending the token. The server requires client certificate possession during the TLS handshake. For an unfamiliar self-signed client, verify the certificate profile and TLS signature and permit only pairing. Require exact pinned fingerprints for all transfer routes. Never accept a claimed ID in place of proof of possession. Do not send tokens until TLS validation succeeds. Disable TLS early data.

- `POST /v1/pair` body `{ "token": "...", "name": "...", "platform": "windows" }`. Verify the token against the live invitation and bind any pending confirmation to the authenticated TLS client fingerprint. Display the pending request on the invitation device. The receiver must explicitly approve before persisting trust. Denial returns `pairing_rejected` and invalidates the invitation.
- Keep the request open while awaiting confirmation, up to the invitation deadline. Return HTTP 200 with `{ "id": "...", "name": "...", "platform": "ios" }` on approval. The redeemer must verify that the returned ID equals the pinned TLS server fingerprint before persisting trust. Only one client fingerprint may redeem an invitation successfully. Allow a bounded reply retry by the same fingerprint and token until the original deadline if the response was lost. Revocation clears trust, invalidates the reply cache and rejects future requests from the peer. It cancels active transfers locally.

## File transfer

All transfer routes require paired mutual TLS. The HTTP client is the sender and the server is the receiver, regardless of platform. A transfer ID is a random lowercase canonical UUIDv4 scoped to an authenticated peer. The file name is a display basename. Receivers choose or derive a safe native destination and must reject traversal, special names or other unsafe destinations. Never overwrite without a separate explicit user decision.

- `POST /v1/transfers` body `{ "id": "...", "name": "sample.bin", "sizeBytes": 123, "sha256": "..." }`. Hash is lowercase 64-character hex SHA-256 calculated over the exact bytes to transmit. Return 201 with a status body reflecting the receiver's local offer. Repeating the same offer for the same peer and ID returns 200 with current status. Different metadata under the same ID returns `conflict`.
- `GET /v1/transfers/{id}` returns 200 and a status body. The sender polls while awaiting the receiver's local accept or reject decision. Poll at most once per second per transfer. Include a finite timeout in client behavior.
- `PUT /v1/transfers/{id}/content` requires state `accepted`, content type `application/octet-stream`, and an exact `Content-Length` equal to the offer. Stream raw bytes to a receiver-owned temporary file. Validate byte count and digest and atomically publish to the chosen safe destination before returning 200 with `completed`. Disallow concurrent/repeated uploads for the same ID. Clean up partial output on failure or cancellation. If a completion response is lost, query status before sending a new offer.
- `DELETE /v1/transfers/{id}` requests cancellation. Return 200 and current status, including repeated deletion. The receiver can also cancel locally. A completion that has already published remains `completed`. Serialize cancellation and final publication.

The status body is `{ "state": "...", "bytesTransferred": 0 }`. A `failed` status includes `"error": { "code": "..." }`. Use these states: `pending` to `accepted`, then `transferring` and `completed`. `rejected`, `cancelled`, and `failed` are terminal alternatives. Allow direct `accepted` to `completed` for an empty file. Bytes are nonnegative JavaScript safe integers, never exceed the offered size, and equal the offered size at completion. Sender reports local streaming progress but only records success after remote completion confirmation. Keep terminal receipts through the running session and long enough for immediate retries.

## Errors and limits

Return JSON `{ "code": "<ErrorCode>" }` for an HTTP error. Use 400 for malformed requests or `unsupported_version`, 403 for `peer_untrusted` or `pairing_rejected`, 404 with `peer_unavailable` for inaccessible or unknown transfer IDs, 409 for `conflict` or `transfer_rejected`, 410 for `pairing_expired`, 413 for control-body size violations, 422 for `integrity_failed`, and 500 for server errors such as `storage_failed`. A client normalizes transport failures as `network_error` and timeouts or unavailable peers as `peer_unavailable`. Clear and localized detail belongs in the local adapter. Never return filesystem paths, session secrets or stack traces to peers. Bound control bodies to 16 KiB and enforce the user's local storage limit before accepting file content.

## App bridge and gestures

Native adapters implement `AppPort`; the host chooses the Tauri invocation and event wiring. Subscribe before initial enumeration and deliver an ordered, full initial snapshot followed by ordered updates, with no lost update across subscription setup. The stop callback is local to the adapter. Return transport errors via `Result`. Use opaque native-owned selection IDs. The UI never receives identity keys or raw filesystem paths. Pairing invitations remain in the trusted UI only. `respond` is the receiver's local UI decision and updates its offer state. A pending redeem resolves after approval, rejection, expiry or cancellation. Reject request IDs and selection IDs outside the current native session.

Gesture commands are local and versioned. The UI opens a short-lived intent for a specific selected file and paired device, or a specific incoming offer. An arm followed by one matching release triggers exactly the same reviewed action as the button. Consume the intent before invoking the action and reset on interruption, blur, timeout, tracking loss, or target change. Reject unmatched or duplicate commands. Camera permission is explicit and frames stay on-device. Camera failure leaves conventional UI controls usable.
